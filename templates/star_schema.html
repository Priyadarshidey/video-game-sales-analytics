What is a star schema?

A star schema is the simplest dimensional-modelling layout for a data warehouse. One central fact table stores numeric measures (things you add up or average) and foreign keys; around it sit small, denormalised dimension tables that describe who, what, where and when. Plotted, the fact table is the centre and the dimensions are the points of a star.

Why it is used: queries need only one join per dimension, aggregations such as "global sales per genre per year" are fast and easy to write, and descriptive text is stored once instead of being repeated on every row.

How it is used in this project {{ impl('actual') }}

The cleaned CSV is split into one fact table and five dimensions in warehouse.transform() and stored in SQLite (datawarehouse.db) by warehouse.load().

  • Fact_Sales - one row per game released on a platform; measures NA, EU, JP, Other and Global sales (million units).
  • Dim_Game / Dim_Platform / Dim_Genre / Dim_Publisher / Dim_Year - each stores every distinct value once with an integer surrogate key.
Grain: one fact row = one game on one platform (e.g. "Wii Sports" on Wii). The same game on another platform is a separate row but reuses the same Game_ID.

Example analytical query (works on the real database)

SELECT ge.Genre, y.Year, ROUND(SUM(f.Global_Sales), 2) AS global_sales
FROM fact_sales f
JOIN dim_genre ge ON ge.Genre_ID = f.Genre_ID
JOIN dim_year  y  ON y.Year_ID   = f.Year_ID
GROUP BY ge.Genre, y.Year
ORDER BY global_sales DESC;
Conceptual mapping: the machine-learning models are trained by train_model.py directly from data/vgsales.csv, not by querying this database. The warehouse holds the same cleaned records, and the ML dataset (Platform, Year, Genre, Publisher → Global_Sales) corresponds to joining Fact_Sales with Dim_Platform, Dim_Year, Dim_Genre and Dim_Publisher.
